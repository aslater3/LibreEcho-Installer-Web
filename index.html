Browser one-shot installer · preview

Install LibreEcho from the browser.

This page runs the install from your browser: it verifies a published release, asks the browser for USB access to the device, and drives the same stages the reviewed host installer drives — fastboot identity, the no-short unlock submission, the recovery-side initial install and a readback receipt after every write.

No Python, no platform tools, no drivers: the browser is the host. Only Chromium-based desktop browsers expose WebUSB.

Preview, not a supported install path. The read-only device query has been tested on Echo hardware; unlock and install writes have not. Run stays disabled until a marker-safe image is qualified. These operations can make a device unrecoverable; the supported route remains the published release and its installation guide.

4 · Device

Query the device in fastboot before any install decision. This reads selected getvar values only; it does not send download, flash, erase or a reboot. The model is inferred from the bootloader-reported product, not independently proven silicon identity. The full serial appears only in the local panel so you can verify the target; the terminal/downloadable log masks it.

If the chooser lists nothing, the device is not presenting an identity this page knows (they are listed in the installer notes). Use the unfiltered chooser — these devices report device class 0, so a class-based filter cannot match them.

Device state: not connected

5 · Pinned Amonet archive (only for a locked device)

Query the device first. Select the matching amonet-*.zip; the browser verifies the entire archive, extracts the exact LK-build fastbrick member and verifies that member's size and SHA-256. With an approved CORS mirror configured, the fetch button obtains the same pinned ZIP automatically. XDA's attachment is not fetched directly from this page because it does not provide a reliable CORS-readable source. No archive or payload is sent to USB by these preparation controls.

6 · Stages

    install progress

      What each stage verifies

      • Release — both checksum inventories and the recovery ZIP/manifest are verified against the release API's digests before any write.
      • Bundle — every selected file is hashed in the browser and compared with the release digest.
      • Device — getvar product, unlock_status and the LK build description are read from the device itself; an unknown target stops the run.
      • Unlock — the pinned build-specific payload is checked locally; fastbrick itself changes early boot-chain storage. A timeout is not accepted as proof of success and is never auto-retried.
      • Recovery — TWRP's ADB serial must match the fastboot serial, and the Kaeru header in expdb must be intact before staging files.
      • Stage — only files that matched the API-anchored normal and TWRP checksum inventories are pushed and re-hashed on the device.
      • Install — the recovery installer's machine-readable receipt is read back after each run; the installer reshapes userdata first when the layout does not match the image contract, and asks for a reboot in between.
