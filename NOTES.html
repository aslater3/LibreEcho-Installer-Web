Browser one-shot installer

What this installer does, and what it refuses to do.

This page is the operator's reference for the browser installer preview. It is published both as part of the development site (dev.libreecho.org/install/) and on its own hostname (install.dev.libreecho.org); every path in the app is relative, so both serve the same files.

The install route

The browser installer implements the same no-short route as the host installer, with the browser as the USB host:

StageWhat happensWhat it checks
ReleaseThe published release inventory is read.The normal and TWRP checksum files, ZIP, manifest and required assets must each match SHA-256 digests reported by the release API. A compatible, marker-safe image qualification is a separate gate.
BundlePayload bytes are selected locally.Each file is hashed in the browser and compared with the release digest before it is used.
Device query (read-only)WebUSB permission prompt, then targeted fastboot getvar reads.Bootloader-reported product/model, lock state, LK and preloader builds, secure/RPMB state, download limit and full serial are shown in the local panel. The serial is masked in the log.
UnlockThe per-LK-build payload is submitted to the brick target.The payload is only eligible if the detected build has a declared entry; the name is reported and the outcome is explicit.
RecoveryADB connects to TWRP.The ADB serial must match the earlier fastboot serial, and expdb must contain an intact Kaeru header before staging or running the ZIP.
StageThe verified files are pushed to /cache/libreecho-bundle.Every pushed file is re-hashed with the device's own sha256sum.
Prepare / InstallThe recovery installer zip is run over ADB, twice if a reboot is required.The installer's own receipt at /cache/libreecho-install-receipt is read back after each run.
VerifyThe device is rebooted.A successful receipt is required; nothing is claimed about runtime behaviour.

Why the payloads come from your own download

Measured from a GitHub Pages origin (the development site), a browser can read api.github.com and raw.githubusercontent.com, but it cannot read github.com/<owner>/<repo>/releases/download/…: the redirect response carries no Access-Control-Allow-Origin header, so the fetch fails before any bytes are readable. The network path itself works — the response simply cannot be read by a page.

Two honest consequences:

  • Default: download the release assets with your browser from the release page, then select them (or the whole folder) in the installer. Include both SHA256SUMS and TWRPINSTALL-SHA256SUMS, the libreecho-install.zip and bundle.manifest. Both inventories are checked against the GitHub release API's asset digests before their listed files are accepted.
  • Optional mirror: a CORS-enabled mirror may help fetch release metadata/checksum listings, but this preview's bundle upload path still requires operator-selected local files. The mirror does not bypass their digest or board gates.

Browser requirements

  • Desktop Chromium-family browser (Chrome, Edge, Brave, Opera). Firefox and Safari do not expose WebUSB.
  • HTTPS (or localhost): WebUSB requires a secure context. GitHub Pages is HTTPS.
  • Direct device connection: a data-capable cable, and no hub in between if the device is fussy about enumeration.
  • After fastbrick, TWRP may enumerate under a different USB identity. Use Grant TWRP USB permission… from a fresh button click if the browser has not authorised that identity; the page checks the original fastboot serial and Kaeru header before any recovery write.

USB identities the installer expects

The device chooser is filtered with the identities an Echo presents in each mode. The page needs no filter entry for a mode it does not use, but a missing entry means an empty chooser, so the unfiltered Show all USB devices… button exists as the escape hatch.

ModeUSB identityHow it presents
Fastboot (stock or unlocked)0bb4:0c01 (measured), 18d1:4ee0–18d1:4ee7, 18d1:d00d, 0e8d:201c, 0e8d:2001Vendor-specific interface with a bulk in/out pair; getvar product answers. 0bb4 is HTC's vendor id and is what this platform has been seen to present in fastboot.
ADB — installed LibreEcho image18d1:d001 (measured)Interface at class 0xFF subclass 0x42 protocol 0x01; product string MT8163-ARM32-ADB.
ADB — TWRP recovery18d1:4ee0–18d1:4ee7, 18d1:d00dSame ADB interface triple; TWRP answers without an authentication token.
Preloader USB download0e8d:2000 (measured)CDC-ACM pair, device class 2, product string like Failed to load LK. This is a download-mode state awaiting a host tool, not fastboot, and it resets on a timer if nothing connects.
Boot ROM (BROM)0e8d:0003Reached with the eMMC short or a cleared preloader header.

These devices report device class 0 with per-interface classes, so a WebUSB classCode filter never matches them: an identity has to be named, or the chooser left unfiltered.

What the installer will not do

  • It never downloads or guesses an unlock payload. Payload selection is bound to the device's own LK build description, and the file must come from the operator.
  • It records a hashed device/payload unlock attempt in local browser storage before submission. A timeout or disconnect is unknown; a second tab or page reload cannot silently resubmit the same payload. Each recovery ZIP phase is similarly recorded before execution and cannot be replayed without manual state classification.
  • The page never directly writes an ASCII FASTBOOT_PLEASE marker. The fastbrick unlock payload itself writes critical boot-chain regions (including Kaeru in expdb, preloader, LK, TEE, recovery and RPMB). A recovery ZIP and boot image are separate execution inputs; no "never writes expdb" claim covers them. Development images and the legacy fastboot reboot-request path can overwrite Kaeru with the marker, so no install is enabled without exact marker-safe image qualification.
  • It never trusts a transfer result: pushed files are re-hashed on the device, and the install result comes from the installer's receipt.
  • It never publishes a device identifier. The full serial is shown only in the local device panel for target confirmation; terminal output and saved logs mask it. A hashed identifier is stored locally to prevent an ambiguous unlock retry.
  • It does not format or reshape partitions from the browser. That work exists in recovery (sgdisk, mke2fs) and is done there, by the installer zip, on the device.

Status

This is a fail-closed preview. The read-only fastboot Query Device stage has been tested over WebUSB on an Echo Dot 2; unlock, recovery and installation have not been hardware-tested from a browser. Run remains disabled until the selected board has a hardware-accepted release and the exact boot image has positive proof that it cannot write FASTBOOT_PLEASE to the Kaeru-bearing expdb. No qualified Biscuit image is shipped. Rehearse performs local/read-only checks only and cannot submit an unlock payload or install ZIP.

Reporting

Use the installer's Save log button and attach the log with the exact release tag, the device mode you started from (stock fastboot or recovery), and the first message that did not match this page. Do not paste device serials, MAC addresses, Wi-Fi credentials or provider tokens.
